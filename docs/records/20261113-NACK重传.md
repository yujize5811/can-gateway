# NACK 回退重传（T6）

- 日期：2026-11-13
- 对应指标：T6 停等 vs 滑窗（重传部分）
- 固件 commit：本记录同批提交

## 1. 我预期发生什么

块传输过程中人为断线 0.5 秒，制造真实丢片。

预期：
1. 接收端发现分片序号跳号，发 **NACK**（`0x51`），内容是「哪个块、从第几片重发」
2. 发送端收到 NACK 后**回退到指定片号**重发（Go-Back-N，后面全部重发）
3. 这个块最终仍然 **256/256 通过**

## 2. 实际发生了什么

### 第一次尝试：什么都没看到

拔线后 `lost` 从 0 涨到 215（确实是丢了），但 PCAN-View 里**没有 NACK 行**，块也照样 PASS。

原因不是没触发，而是 **NACK 和 ACK 用了同一个 CAN ID**（都是 `NODE_ID + 0x300`）。
PCAN-View 按 ID 分组显示，同一 ID 只保留最新一帧 —— NACK 刚发出去就被下一个 ACK 覆盖了。

**修复**：NACK 改用独立 ID `NODE_ID + 0x400`（A `0x601` / B `0x602`）。

### 第二次尝试：看到了

```
602h   51 00 07 48 00 00 00 4B
```

解码：`type=0x51`（NACK）、`block=7`、**`从第 72 片开始重发`**、`nakCnt=0`、`Count=1`。

结果两边都通过：

```
501h   50 05 07 00 00 01 06 35     A：block=7  PASS  256/256  okCnt=6
502h   50 06 07 00 00 01 07 49     B：block=7  PASS  256/256  okCnt=7
```

`lost` 计数：A 从 0 涨到 **57**、B 从 0 涨到 **64**（双向都断过）。

**NACK 只发了一次（Count=1）就恢复**，说明 50 ms 限速生效，没有刷屏。

## 3. 差在哪

第一次「什么都没看到」不是功能没生效，是**观测手段有盲区**：
两个不同的语义（重传请求 / 完成确认）共用一个 ID，在分析仪上就是一行，后到的覆盖先到的。

这和之前「心跳和数据共用 0x201」是同一类错误 —— **CAN ID 不只是地址，也是频道**。

第二次把 NACK 挪到 `0x6xx`，立刻可见。

## 4. 结论·下一步

- T6 重传链路闭环：**丢片 → NACK 定位到片号 → 回退重发 → 整包 CRC32 仍然通过**
- Go-Back-N 的选择依据：总线负载只有 1.1%，重发 200 片花 44 ms，占块周期 5.1 秒的 0.9%，比实现选择重传便宜
- 已知局限：断线超过 2.7 秒（128 帧）会被判成对方重启 → 整块作废。这个窗口由 `gap < 128` 的阈值决定，需要靠心跳/连接状态来区分「短暂丢包」和「真断链」，是 T7 的内容
