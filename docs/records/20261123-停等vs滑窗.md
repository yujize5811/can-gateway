# 停等 vs 滑窗：1 KB 块的耗时对照

- 日期：2026-11-23
- 对应指标：README 指标表「吞吐 — 1 KB 停等 vs 滑窗耗时」
- 固件：`Code=8056`，`BLK_WINDOW` 是唯一变量（1 = 停等，4 = 滑窗）

## 1. 我预期发生什么

原先的估算来自 `docs/02-protocol.md`：停等 8.6 s、滑窗 1.7 s，差 5 倍。

理由是：停等每片都要等一个 20 ms 的循环，滑窗一轮能塞 4 片，所以应该快 4 倍。

## 2. 实际发生了什么

改的代码只有一行：把「每轮发 1 片」改成「每轮最多发 `BLK_WINDOW` 片」的 `for` 循环。

| 组 | `301h` Cycle Time | 1 KB 块耗时 | 数据来源 |
|---|---|---|---|
| 停等（窗口 1） | 21.0 ms | 256 × 21 ms = **5376 ms** | T4 72 小时压测期间的常态值 |
| 滑窗（窗口 4） | **0.2 ms** | **2728 ms** | 实测 |

块耗时的算法：`501h` 的 ACK 间隔减去固定间隔。

```
7748.6 ms − (5000 ms 空档 + 21 ms 一个循环) = 2728 ms
```

两块板的 ACK 间隔一致（A 7748.6 ms / B 7748.3 ms），块号分别 10 / 05，**均为 PASS 256/256**——放大窗口没有造成丢片。

**提速只有 1.97 倍，不是 4 倍。**

## 3. 差在哪

`Cycle Time` 从 21.0 ms 掉到 0.2 ms，说明**帧已经背靠背在发了**（一帧 111 位 ÷ 500 kbps = 0.222 ms）。

那 2.7 秒花在哪？

```
2728 ms ÷ 256 片 = 10.65 ms/片
一个主循环 21 ms，平均只塞进去 1.97 片
```

**每轮只发出 2 片，不是 4 片。**

原因是硬件限制：**STM32F103 只有 3 个 CAN 发送邮箱，而每个循环都要先发一帧数据帧（0x201/0x202），占掉 1 个。剩 2 个给分片。**

窗口设成 4、8、100 结果都一样——第三个分片一进邮箱就返回 `HAL_ERROR`，只能 `break`，等下一轮。

所以真正的瓶颈是：

| 资源 | 耗时 |
|---|---|
| 总线带宽（256 片 × 0.222 ms） | **57 ms** |
| 主循环节拍（256 片 ÷ 2 片/轮 × 21 ms） | **2688 ms** |

**花了 2.7 秒，其中 2.63 秒在等 `HAL_Delay(20)`。**

## 4. 结论·下一步

- **停等 5.38 s → 滑窗 2.73 s，提速 1.97 倍。** 原估算的「8.6 s → 1.7 s」两处都不准：停等实际是 5.38 s（原估算按 20 帧/s 算成 12.8 s 又取整成 8.6 s，口径混乱），滑窗也没到 1.7 s。
- **提速天花板由主循环节拍决定，不是总线。** 想让滑窗真正发挥，必须改驱动方式：
  - 方案 A：块发送期间把 `HAL_Delay(20)` 降到 1~2 ms（数据帧周期会被压缩，属于副作用）；
  - 方案 B：块发送放进 CAN 发送完成中断，或改成"每轮把邮箱塞满再退"的紧密循环；
  - 方案 C：改成 TCP 式的滑动窗口，等 ACK 再推进，而不是按循环节拍推。
- 本次不做改造：它不影响「1 KB 块能不能传对」这个核心结论，只影响吞吐上限，列入已知限制（见 `docs/02-protocol.md`）。
