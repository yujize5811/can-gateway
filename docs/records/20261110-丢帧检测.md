# 丢帧检测（序号缺口法）

- 日期：2026-11-10
- 对应指标：T8 离线/上线（部分）、T4 长时间稳定性（前置）
- 固件 commit：本记录同批提交

## 1. 我预期发生什么

双节点互发，两块板都带 16 位 `lostCnt` 计数。

- 静置 60 秒以上，`lostCnt` 应该一直是 0
- 拔掉一根 CAN 线 2 秒再插回，`lostCnt` 应该增加约 95（2 秒 × 47.6 帧/秒）

原理：每帧带 `seq`（0~255 循环），接收端算 `gap = 本次 seq - 上次 seq - 1`。
`gap` 在 1~127 之间表示中间少了这么多帧；`gap >= 128` 判为对方重启，只重新对齐不计数。

## 2. 实际发生了什么

### 静置基线

```
201h   21 D4  D4 1C  00 00  00  B3     A: cnt=7380  lost=0  rxErr=0
202h   21 11  11 1C  00 00  00  16     B: cnt=7185  lost=0  rxErr=0
```

两板各跑 7000 多帧（约 155 秒），`lost` 和 `rxErr` 全程为 0，周期 21.0 ms。

### 拔线 2 秒

```
201h   21 73  73 0A  00 00  00  72     A: lost=0      ← 没反应
202h   21 AE  AE 0A  67 00  00  FE     B: lost=103    ← 正确
```

B 板从 0 涨到 103，约 2.2 秒的帧量，符合预期。

A 板没变。

## 3. 差在哪

现象：同样是拔线，B 记了 103 帧，A 记了 0。

排查：不是 A 的代码有问题——两块烧的是同一份固件，只有 `NODE_ID` 不同。

根因：**序号缺口法有一个前提——「还能收到帧」**。

- 完全断线时，A 一帧都收不到，没有新帧就没有新 `seq`，**没有输入，自然也发现不了缺口**
- 重新接上后，下一帧的 `seq` 已经跳过了 100 多，`gap` 超过 127，被判成「对方重启」→ 只 `reSync`，不计丢帧

所以 A 的 0 不是 bug，是**这个方法的能力边界**。

## 4. 结论·下一步

- **序号缺口能测「偶发丢帧」**（总线干扰、FIFO 溢出、仲裁失败），不能测「完全断链」
- 完全断链要靠**超时**：心跳 1 Hz，连续 3 个周期（3 秒）收不到就判离线——这就是 T8 的内容
- 两种机制互补：缺口法回答「丢了多少」，超时法回答「还在不在」

这属于「知道自己的检测手段测不到什么」，比检测本身更重要。
