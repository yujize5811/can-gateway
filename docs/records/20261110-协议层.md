# 协议层跑通：CAN-GW v1 组帧 + CRC8 校验

- 日期：2026-11-10
- 对应指标：T2 业务负载 / 帧格式正确性
- 固件 commit：Code=6074（含 can_proto.c）

## 1. 我预期发生什么

两块板都跑新固件后，PCAN-View 上 `201h` 和 `202h` 的 Data 应该满足：

- 第 1 字节固定 `21`（type = 数据帧）
- 第 2 字节是 seq，0~255 循环
- 第 5 字节是 rxOk，两边都往上走
- 第 6 字节是 rxErr，两边都保持 `00`
- 第 8 字节是 CRC8，每帧都变

## 2. 实际发生了什么

```
201h   21 4F 61 06 0B 00 00 CE   21.0 ms    Count 1072
202h   21 0B 0B 05 0B 00 00 57   21.0 ms    Count 1073
```

拆开 A 板的帧：

| 字节 | 值 | 含义 |
|---|---|---|
| [0] | `21` | type = 数据帧 |
| [1] | `4F` | seq = 79 |
| [2][3] | `61 06` | cnt = 0x0661 = 1633 |
| [4] | `0B` | rxOk = 11 |
| [5] | `00` | rxErr = 0 |
| [6] | `00` | 保留 |
| [7] | `CE` | CRC8 |

两边 `rxOk` 都是 11，`rxErr` 都是 0。

## 3. 差在哪

没有差。

CRC 用 Python 独立复算，两帧都对上：

```
A: 21 4F 61 06 0B 00 00  -> 0xCE  (板子发的 0xCE)
B: 21 0B 0B 05 0B 00 00  -> 0x57  (板子发的 0x57)
```

`rxOk` 两边都是 11，是因为两块板几乎同时复位，收到的帧数一致。

## 4. 结论·下一步

**协议层三项全部成立：组帧正确、CRC 正确、错误帧能被识别并拒绝。**

验证「拒绝」的那一轮记录：把 B 板留在旧固件上时，A 板的 `rxErr` 涨到 30，
因为它发出的帧第 1 字节是 `1F`（旧代码的计数值），第 8 字节恒为 `00`，
CRC 校验必然失败，A 板把它们全部拒收。这证明校验不是摆设。

下一步：ID 分段（0x1xx 心跳 / 0x3xx 命令 / 0x5xx ACK），以及序列号丢失检测。
