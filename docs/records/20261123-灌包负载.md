# T3 灌包：总线负载上限

- 日期：2026-11-23
- 对应指标：T3 灌包时总线负载上限
- 固件 commit：本次记录同批提交

## 1. 我预期发生什么

500 kbps 下，一帧标准数据帧（8 字节）在总线上占 **111 位**（SOF 1 + 仲裁 12 + 控制 6 + 数据 64 + CRC 15 + CRC 界定 1 + ACK 2 + EOF 7 + IFS 3）。

```
111 位 ÷ 500 000 bps = 0.222 ms/帧
100 % 负载 = 1 ÷ 0.222 ms ≈ 4500 帧/s
40 % 负载 ≈ 1800 帧/s
```

目标：让 A 板以可控速率连续发帧，测出「帧率—负载」曲线，以及总线打满时另一个节点会怎样。

## 2. 实际发生了什么

灌包分支实现在 `main.c` 的 `USER CODE BEGIN 3` 里，只在 A 板（`NODE_ID == 0x201u`）且上电前 300 秒生效：

```c
if ((NODE_ID == 0x201u) && (HAL_GetTick() < 300000u))
{
  for (bk = 0u; bk < 3u; bk++)          /* 每轮最多塞 3 帧，邮箱满即 break */
  {
    cangw_pack(txBuf, CANGW_TYPE_DATA, seq, payload);
    if (HAL_CAN_AddTxMessage(&hcan, &txHeader, txBuf, &txMailbox) != HAL_OK) break;
    cnt++;
    seq++;
  }
#if (BURST_PACE_MS > 0u)
  HAL_Delay(BURST_PACE_MS);              /* 节拍可调：0 = 不歇 */
#endif
  continue;
}
```

用 `102h` 心跳（1 Hz）当秒表，三组数据：

| 节拍配置 | `201h` 增量 | 经过时间 | 帧率 | 总线负载 |
|---|---|---|---|---|
| 每轮 2 帧 + `HAL_Delay(1)` | 38 437 | 31 s | **1240 帧/s** | **27.6 %** |
| 每轮 3 帧 + `HAL_Delay(1)` | 14 153 | 9.88 s | **1433 帧/s** | **31.8 %** |
| 每轮 3 帧 + 不歇（`BURST_PACE_MS 0`） | 18 331 | ≈4 s | **≈4500 帧/s** | **≈100 %** |

第三组同时观察到的现象：

- `201h` Cycle Time：`21.0 ms → 0.3 ms`（帧已背靠背）
- `202h`（B 板）增量只有 **118 帧 / 4 秒 = 29 帧/s**，被从 47.6 压到 **61 %**
- `301h` / `302h` 的 Count 在两图之间**完全冻结**（5344 / 4736 没动）——多帧块传输停滞
- `101h`（A 的心跳）在灌包期间消失（`continue` 跳过了心跳发送，属预期）

## 3. 差在哪

**第一、二组没到 40 %，不是总线的问题，是节拍的问题。**

反推第二组：每轮 `9.88 s ÷ (14153 ÷ 3) = 2.09 ms`。其中 3 帧在总线上只要 `3 × 0.222 = 0.67 ms`，剩下的 **1.42 ms 全花在 `HAL_Delay(1)` 上**——SysTick 只有 1 ms 分辨率，"等 1 ms"平均要等 1.5 个滴答。

所以这个结构的物理天花板约 **1500 帧/s（33 %）**，用 1 ms 节拍够不着 40 %。要稳定跑到 40 % 必须换成定时器中断驱动，而不是主循环里 `HAL_Delay`。

**顺带纠正一条旧账**：之前文档里写"40 % ≈ 1500 帧/s"是错的。`1500 × 0.222 ms = 333 ms/s = 33.3 %`，真 40 % 需要 **1800 帧/s**。

**第三组的价值不在帧率，在"从属节点会怎样"。** A 抢满带宽时，B 的数据帧被压到 61 %，块传输彻底停滞——CAN 的仲裁保证高优先级帧先走，但它是**非抢占式**的：一旦 A 占住总线，B 只能等每个间隙。

## 4. 结论·下一步

- **可控负载曲线**：27.6 % → 31.8 % → 100 %，中间缺 40~80 % 的取样点
- **总线上限**：≈ 4500 帧/s（理论值，实测顶到即视为饱和）
- **饱和时的副作用**（比帧率更值钱）：从属节点有效带宽压到 61 %、多帧块传输完全停滞
- 若要补齐 40~80 % 的取样点，把 `HAL_Delay` 换成硬件定时器触发的发送槽；本次不做（不影响结论，且会把项目拖进驱动层重构）

一句话结论：**这个网关在 1 % 负载下跑 72 小时零故障，在 100 % 负载下会饿死邻居。两个边界都测到了。**
