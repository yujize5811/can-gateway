# 多帧块传输（1 KB 分片）

- 日期：2026-11-11
- 对应指标：T5 多帧传输
- 固件 commit：本记录同批提交

## 1. 我预期发生什么

1 KB 的块拆成 256 片，每片 4 字节，用三种帧走同一条车道：

| 帧 | 类型码 | 内容 |
|---|---|---|
| START | `0x3F` | 块号 + 总长度 |
| FRAG | `0x40` | 片序号 + 4 字节数据 |
| END | `0x41` | 整包 CRC32（大端 4 字节） |

- A 板车道 `0x301`，B 板车道 `0x302`（节点号 + 0x100）
- 接收方校验整包 CRC32，回一个 ACK 走 `0x501`/`0x502`
- ACK 内容：`[块号][0=通过/1=失败][收到的片数低][片数高][累计通过块数]`

预期：两边每 10 秒左右传完一块，ACK 显示 `256/256` 且 `通过`。

## 2. 实际发生了什么

```
101h  A: uptime=832 秒    在线
102h  B: uptime=1206 秒   在线
201h  A: 39627 帧  lost=75
202h  B: 57446 帧  lost=0
501h  A 的 ACK: 块 115  失败  218/256 片  累计通过 39 块
502h  B 的 ACK: 块 79   通过  256/256 片  累计通过 79 块
```

- **B 侧 79 块全部通过**，一片不差
- **A 侧 40 块里失败 1 块**，只收到 218 片
- 双方的 `Count` 与 `uptime` 折算都是 47.5 帧/秒，与 21 ms 周期吻合
- 块传输期间数据帧被挤占，帧率从 50 掉到 47.6，这是预期内的带宽占用

## 3. 差在哪

现象：A 少的不是 38 片，而是 **丢 1 片 + 连锁作废 37 片**。

排查：接收代码里判断片序号的写法是

```c
if (idx == blkRxExpect) { 收下这一片; blkRxExpect++; }
else                    { 丢弃 }
```

只要中间少了一片，后面所有片的 `idx` 都对不上 `blkRxExpect`，
于是**即使它们完好无损地到了，也会被当成错序丢掉**，直到 END 才发现片数不够、CRC 对不上。

根因：**协议只有"检测"，没有"重传"**。丢了就是丢了，整块报废等下一块。

另外 A 侧 `lost=75` 而 B 侧为 0，"丢"始终跟着 A 板走——这一项仍未定位，
下一步用"对调收发器模块"做对照实验（与 11-10 那次同样的手法）。

## 4. 结论·下一步

- **T5 主链路成立**：分片、序号、整包 CRC32、ACK 全部跑通，B 侧 79/79 全过
- **缺陷已知**：无重传、无 NACK、无滑窗，对丢包的容忍度为 0 片
- 这三条正是 T6 的内容：END 之后回 NACK 带缺失片位图，发送方重发缺失片
- A 侧连续丢帧另案处理：先对调收发器模块，把"硬件问题"和"时序问题"分开

**这段的价值不在"传成功了"，而在"清楚地知道它在什么条件下会失败，以及失败时会烂成什么样"。**
