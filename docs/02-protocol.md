# CAN-GW v1 应用层协议

自定义协议，不是 ISO-TP，也不兼容任何第三方设备。**目的只是让两块板在业务负载下跑得干净。**

## 1. 11 位 ID 分段

用 ID 高位区分功能，低位放节点号（0–15）：

| ID 范围 | 用途 | 方向 | 说明 |
|---|---|---|---|
| `0x1xx` | 心跳 / 状态 | 节点 → 网关 | 1 Hz，带版本号与错误计数 |
| `0x2xx` | 周期数据 | 节点 → 网关 | 8 字节定长，20 ms |
| `0x3xx` | 命令下发 | 网关 → 节点 | 1 字节命令 + 参数 |
| `0x4xx` | 多帧传输 | 双向 | FF / CF 分片 |
| `0x5xx` | ACK / NACK | 双向 | 确认或请求重发 |

`xx` 的低 4 位是节点号，高 4 位留给子类型。例如 `0x201` = 节点 1 的周期数据，`0x212` = 节点 2 的子类型 1。

## 2. 单帧负载（8 字节）

```
[类型][序号][D0][D1][D2][D3][D4][CRC8]
 ↑      ↑    └──────── 业务数据 ────────┘
 │      └─ 0–255 循环，用于丢帧检测
 └─ 命令码 / 数据类型
```

**序号是关键**：接收端按序号连续性判断有没有丢帧。没有序号，只能靠「感觉」，无法量化。

CRC8 覆盖前 7 字节，多项式 `0x07`（CRC-8/ATM），初值 0x00。

## 3. 多帧传输（1 KB → 172 帧）

1 KB 数据 = 1024 字节，每帧有效负载 6 字节 → 172 帧（1 个 FF + 171 个 CF）。

**FF（首帧）**，ID `0x4xx`：

```
[0x1F][总长H][总长L][SN=0][D0][D1][D2][CRC8]
                              └─ 6 字节有效 ┘
```

**CF（续帧）**，ID `0x4xx`，SN 从 1 递增到 255 后回绕：

```
[0x2C][SN][D0][D1][D2][D3][D4][CRC8]
```

整包再做一次 CRC32（项目里用软件实现，多项式 `0x04C11DB7`），全部收齐后校验。

**为什么两层校验**：CRC8 挡单帧误码，CRC32 挡「每帧都对但顺序错/丢了一帧」——这种情况单帧校验永远发现不了。

## 4. 两种流控，用来讲优化

### v1：停等（Stop-and-Wait）

发一帧 → 等 ACK → 发下一帧。

```
1 KB 传输 ≈ 8.6 s
吞吐 ≈ 20 帧/s
```

慢的原因不是总线，是**等待往返延迟**。500 kbps 下单帧才 220 µs，其余 49.8 ms 全在等。

### v2：滑动窗口（窗口 4）

连续发 4 帧不停，超时或 NACK 才重传。

```
1 KB 传输 ≈ 1.7 s
吞吐 ≈ 100 帧/s
```

**简历上写「1 KB 传输从 8.6 s 优化到 1.7 s」，不要写「实现了滑动窗口」。** 前者是结果，后者是名词。

## 5. 心跳与离线判定

- 节点每 1 Hz 发 `0x1xx`，带 `version` 和 `error_count`
- 网关超过 **3 个周期（3 s）** 没收到才判离线

**为什么不是 1 s**：刚好一个周期就判，任何一次总线抖动都会误判成离线。3 个周期能把偶发丢帧过滤掉。

离线后：网关把该节点数据标记为失效，继续发其他节点；节点恢复后 2 s 内自动重新上线（不需要重启）。

## 6. 命令与确认

```
网关 → 节点  0x3xx  [cmd][param...][CRC8]
节点 → 网关  0x5xx  [0x00][SN][CRC8]    ACK
              0x5xx  [0xFF][SN][错误码][CRC8]  NACK
```

超时 100 ms 未收到 ACK 则重发，最多 3 次，3 次失败上报错误。

## 7. 已知限制

- 没有优先级设计，所有周期数据同优先级 —— 负载高时低 ID 先赢仲裁，纯属运气
- 没有时间同步，跨节点时序只能做到毫秒级
- 滑窗窗口固定为 4，没有根据 RTT 自适应
