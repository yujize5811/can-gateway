## 坑 1：买到的 CBT6 是被改丝印的 C8T6

- **日期**：2026-11-01
- **现象**：按 128 KB 规划 Flash 分区（Boot 16K + App 48K + 下载区 48K + 参数区 2K），编译能过，下载到 `0x0800C000` 之后全 0，程序跑飞。
- **排查过程**：
  1. 先怀疑链接脚本，改 `stm32f103xb.ld` 的 FLASH 长度 → 无变化
  2. 换 ST-Link Utility 读芯片信息 → 显示 64 KB
  3. 读内存 `0x1FFFF7E0`（Flash size 寄存器）→ 返回 `0x0040` = 64 KB
- **根因**：商家把 C8T6 的丝印改成 CBT6 卖。**丝印不可信，寄存器才可信。**
- **修复**：退货换 3 块真正 CBT6，复测 `0x1FFFF7E0 == 0x0080`。
- **代价**：两天，全部固件返工。

**验货脚本**（每块板到货第一件事）：

```c
uint16_t flash_kb = *(volatile uint16_t *)0x1FFFF7E0;
printf("Flash = %u KB\n", flash_kb);   // 期望 128
```

## 坑 2：终端电阻接成串联

- **日期**：2026-11-0_
- **现象**：两块板接好，分析仪抓不到任何帧；A 板 `can.send()` 报错；`CAN_ESR.TEC` 一路涨到 255 进 Bus-Off。
- **排查过程**：
  1. 先怀疑代码，换成官方 HAL 例程 → 一样
  2. 换线、换收发器 → 一样
  3. **断电量总线电阻** → 万用表显示 OL（开路）

**正确接法**：120 Ω **跨接**（并联）在 CANH 与 CANL 之间，两端各一个。

```
CANH ──┬──────────────┬── CANH
      [120Ω]        [120Ω]
CANL ──┴──────────────┴── CANL
     末端 1          末端 2
```

- **根因**：把电阻串在了 CANH 或 CANL 线上，等效把总线断开。
- **修复**：改成并联，断电量得 ≈ 60 Ω。
- **代价**：半天。

**判断口诀**：断电量 CANH–CANL，**60 Ω 正常，120 Ω 只接了一个，40 Ω 接了三个，OL 就是开路**。

## 坑 3：单板发帧报 `TxError`

- **日期**：2026-11-0_
- **现象**：只插一块板时，`bus.send(msg)` 抛 `can.exceptions.CanOperationError`，板端一直重传，TEC 涨到 255。
- **排查过程**：
  1. 以为位定时错 → 用分析仪读回，500 kbps 正确
  2. 以为收发器坏 → 换一块，一样
  3. 查 CANTX 波形 → 帧发出去了一部分，在 ACK 位被拉低失败
- **根因**：CAN 协议要求**每个数据帧都必须有至少一个节点在 ACK 槽回应显性电平**。单板时没人应答，发送方认为出错，自动重传。
- **修复**：不是 bug，不用修。插上第二块板即正常。调试时如果想单板验证，可以开**回环模式**（`CAN_MCR.LBKM`）。
- **代价**：半小时（差点去换芯片）。

## 坑 4：TJA1050 接非 FT 引脚

- **日期**：2026-11-0_
- **现象**：换成 TJA1050 模块后，PA11 这个引脚上电就发烫，偶尔进 HardFault。
- **排查过程**：
  1. 查原理图 → TJA1050 是 **5 V 供电**，`RXD` 输出也是 5 V 电平
  2. 查 F103 数据手册 → PA11 不是 5 V 容忍（FT）引脚
- **根因**：5 V 输出直接灌进 3.3 V IO，靠内部 ESD 二极管泄放，长期会损坏。
- **修复**：改用 **SN65HVD230**（3.3 V 供电，输出 3.3 V），与 MCU 电平天然匹配。

**顺带结论**：F103 的 PA11/PA12 恰好是 USB 引脚，标注为 FT（5 V 容忍），所以这两根能接 5 V。**但换成别的引脚就会烧**，不要凭「试过一次没事」就下结论。
## 2026-11-04 CubeMX 默认 No Debug，烧一次就锁死

### 现象
第一块板子下载成功后，之后怎么连都是 `No target connected`。
换同批次的新板子，第一次能烧，烧完同样连不上。

### 排查过程
- 换板子 → 新板第一次成功、第二次失败 → 排除板子坏
- 换杜邦线、换 USB 口、把 SWD 时钟从 10 MHz 降到 200 kHz → 无效
- `Connect` 从 `under Reset` 改回 `Normal` → 报错变成 `Could not stop Cortex-M device`
- 按住 RST 再点下载 → 还是这个错（复位期间核心停着，halt 不进去）
- 拆开生成代码：`Core/Src/stm32f1xx_hal_msp.c:76` 是 `__HAL_AFIO_REMAP_SWJ_DISABLE();`

### 根因
CubeMX 新建工程时 `System Core → SYS → Debug` 默认是 `No Debug`。
生成的 `HAL_MspInit()` 会把 PA13/PA14 从 SWD 改成普通 IO。
`HAL_Init()` 是 `main()` 的第一行，所以上电约 4 µs 后 SWD 就被关掉。

第一次能烧，是因为芯片是空的，没有程序去关它。

### 修复
- `.ioc` 里 SYS Debug 改成 `Serial Wire`
- 生成后确认那句变成 `__HAL_AFIO_REMAP_SWJ_NOJTAG();`
- 已经被锁的芯片：按住 BOOT0 → 按 NRST → 松手，进 bootloader 后下载

### 代价
一整个上午，外加一度怀疑三块板子全坏。

## 5. 单板发帧时 PCAN-View 一帧都收不到

- **日期**：2026-11-04
- **现象**：CAN 初始化、下载、运行全部正常，PCAN-View 状态 OK、Overruns 0，但 Receive 窗口始终 Empty。
- **排查过程**：
  1. 逐层核对时钟（72M / APB1 36M）、位定时（8/6/2/1）、引脚（PA11/PA12）、模式（Normal）、`HAL_CAN_Start` —— 全对。
  2. 查 `can_gw.map`，确认 `main.o` 确实引用了 `HAL_CAN_AddTxMessage` —— 发帧代码真的在固件里。
  3. 换板、换线、对调 RX/TX、对调 CANH/CANL —— 都无效。
  4. 关键一步：在调试器里看 `cnt` 变量。
- **根因**：HVD230 模块损坏，收发器不工作，总线上没有节点产生 ACK。表面现象被 `cnt` 这个变量暴露：`cnt` 一直等于 **3** 且不再增长。F103 的 CAN 只有 3 个发送邮箱，帧被对端 ACK 后邮箱才释放。停在 3 = 三个邮箱全被占满 = **发出去的帧从来没有被 ACK 过**。CAN 的 ACK 由接收方硬件拉低，没人拉低就永远重发（AutoRetransmission=Enable）。所以"PCAN 一帧都没有"是必然的，不是 PCAN 的显示问题。
- **修复**：更换一块新的 SN65HVD230 模块后立即恢复。旧模块已损坏（此前曾误接到 5V，SN65HVD230 是 3.3V 器件，5V 会击穿）。
- **代价**：从 11-03 晚到 11-04 晚，约一天。
- **教训**：SN65HVD230 只能接 3.3V，接 5V 当场击穿，而且外壳看不出来、指示灯也不亮（模块没有灯）。`cnt` 停在邮箱数量（F103 是 3）是"没有 ACK"的指纹。以后遇到"发不出去"，先看这个数，再看 CAN1->ESR 的 TEC 值：TEC 涨到 128 = 进入 error-passive，同样说明没人 ACK。

## 6. 加了接收代码后，板子"有电但不发帧"

- **日期**：2026-11-09
- **现象**：给板子加上接收功能后，PCAN-View 上这条 ID 完全消失。电源灯亮着，Build 也 0 Error，看起来一切正常。
- **排查过程**：
  1. 先怀疑没下载成功 → 回看 Build Output，`Build Time Elapsed: 00:00:00`，根本没重新编译（见第 7 条）。
  2. 强制 Rebuild 后仍然不发帧。
  3. 逐行看 `USER CODE 2` 的顺序，发现 `HAL_CAN_ConfigFilter()` 写在 `HAL_CAN_Start()` 之后。
- **根因**：`HAL_CAN_ConfigFilter()` 内部要先让 CAN 进入 Init 模式、配完再退出。外设已经 `Start` 过再调用会返回 `HAL_ERROR`，代码走到 `Error_Handler()` 的 `while(1)` 里死循环。板子上电、灯亮、但一条指令都不再执行——**"活着但不干活"**。
- **修复**：顺序改成 `HAL_CAN_ConfigFilter()` → `HAL_CAN_Start()`。
- **代价**：约 40 分钟，中间误以为是板子没电、USB 口不够、杜邦线接触不良。
- **教训**：`Error_Handler()` 是一个没有输出、没有日志的死循环。任何 `if (xxx != HAL_OK) Error_Handler();` 都在给自己埋雷。判断"程序有没有跑到 main 的 while(1)"，比判断"板子有没有坏"更值得先做。

## 7. Build Output 显示 0 Error，但 `Build Time Elapsed: 00:00:00`

- **日期**：2026-11-09
- **现象**：用外部工具改了 `main.c` 之后，Keil 里点 Build，输出 `0 Error(s), 0 Warning(s)`，看起来编译成功。但下载后现象毫无变化。
- **排查过程**：
  1. 反复确认代码改动位置正确。
  2. 注意到 `Build Time Elapsed: 00:00:00`，且没有任何 `compiling xxx.c...` 行。
  3. 关掉 Keil 重新打开工程 → Rebuild → 出现 `compiling main.c...` 与 `linking...`，耗时 3 秒，`Program Size: Code=4524`。
- **根因**：Keil 的编辑缓冲里还是旧内容（外部修改后没有点重新加载），增量构建认为"文件没变"，直接跳过编译，把旧的 `.axf` 又链接了一遍。`0 Error` 是真的，但编译的对象是旧代码。
- **修复**：外部改过文件后，必须 **关掉工程重开** 或确认弹窗点「是(Y)」重新加载，然后 **Rebuild**，并确认 `Build Time Elapsed` 不为 0。
- **代价**：两次无效烧录，每次都要重新拔插 ST-Link。
- **教训**：`0 Error` 不等于"改动能生效"。判断标准是 **有没有出现 `compiling 目标文件` 那一行**，以及 **Program Size 有没有变化**。

## 8. 幻影丢帧：seq 递增了，帧却没发出去

- 日期：2026-11-10
- **现象**：双节点静置，什么都没动，`lostCnt` 每秒涨几帧到几十帧，但 `rxErr`（CRC 失败）一直是 0。
- **排查**：
  1. 先怀疑总线质量 → 把 120 Ω 终端电阻测了一遍，60 Ω 正常。
  2. 再怀疑 CRC → 逐帧用 Python 复算，全部通过。
  3. 缩小到"序号对不上但数据没错"，去看发送端代码。
- **根因**：`cangw_pack(buf, type, seq, payload); seq++;` 与
  `if (HAL_CAN_AddTxMessage(...) == HAL_OK) cnt++;` 是分开的。
  **发送失败（3 个邮箱全满或仲裁失败）时 `seq` 照样加 1**，对端看到序号缺口就记一笔"丢帧"——
  丢的是一帧**从来没发出去过**的数据。这是自己制造的假故障。
- **修复**：把 `seq++` 移进 `HAL_OK` 分支，让 `seq` 只对真正发出的帧递增。
- **代价**：误判了两轮，每轮重烧两块板。
- **教训**：**计数器的语义要和物理事实对齐**。"第几次尝试发"和"第几帧发出去"是两回事，
  混用就会统计出不存在的问题。

## 9. 真丢帧：每轮只从 FIFO 取一帧

- 日期：2026-11-10
- **现象**：修完第 8 条后，`lostCnt` 不再暴涨，但仍有零星增长；两块板表现不对称（一块几十、一块为零）。
- **排查**：两块烧同一份固件，只差 `NODE_ID`，问题跟着某一块板走 → 排除代码逻辑，怀疑时序。
- **根因**：接收端写的是
  `if (HAL_CAN_GetRxMessage(...) == HAL_OK) { ... }`，
  **一轮循环只取一帧**。CAN 接收 FIFO 只有 3 级深，而本工程的循环节拍是 21 ms、对方也是 21 ms 发一帧，
  等于没有余量。某一轮被仲裁重发或 `HAL_Delay` 抖动拖长，FIFO 攒满第 4 帧就直接溢出丢弃。
- **修复**：改成 `while (HAL_CAN_GetRxMessage(...) == HAL_OK)`，
  一轮把 FIFO 取空为止（取空后返回 `HAL_ERROR`，循环自然退出）。
- **验证**：改后 A 7380 帧、B 7185 帧连续跑 155 秒，`lostCnt` 全程为 0。
- **代价**：又烧了两轮板。
- **教训**：**接收端要"取空"，不能"每轮取一个"。** 中断里也一样——
  中断只负责把数据搬进环形缓冲，而不解决"一帧一轮"的问题。

## 10. 心跳和数据共用同一个 CAN ID，PCAN-View 里看不出谁停了

- 日期：2026-11-11
- **现象**：第一版心跳直接借用数据帧的 ID（0x201），结果 PCAN-View 的 `0x201` 那一行被两种帧轮流覆盖：
  数据帧 21 ms 一帧、心跳 1 秒一帧，屏幕上看到的“最后一次数据”不停在两类内容之间跳变。
  一旦某侧停发，剩下的那一类仍然在刷新，**看起来一切正常**。
- **根因**：PCAN-View 的 Receive 窗口按 ID 聚合，同一 ID 只显示最后一帧。
  把不同周期的消息塞进同一个 ID，等于把两条时间线压成一条。
- **修复**：心跳用独立 ID——节点号减 0x100（A：0x201→0x101，B：0x202→0x102）。
  数据 21 ms 一行、心跳 1 秒一行，四个 ID 各占一行，谁停了立刻能看出来。
- **代价**：一次重烧。
- **教训**：**总线 ID 不只是“地址”，也是“频道”。** 不同周期、不同语义的消息要分频道，
  否则调试工具会把它们混成一个，掩盖故障。

## 11. 诊断帧和结果帧用了同一个 ID，导致"发了却看不见"

- 日期：2026-11-13
- **现象**：注入丢包验证 NACK 重传。`lost` 从 0 涨到 215，说明帧确实丢了、重传逻辑应该被触发，
  但 PCAN-View 里**找不到任何 NACK 行**，而块仍然 PASS —— 无法判断"没触发"还是"触发了但看不见"。
- **排查**：翻代码发现 `HAL_CAN_AddTxMessage(&hcan, &ackHeader, nakBuf, ...)` ——
  NACK 复用了整包 ACK 的 `ackHeader`（`NODE_ID + 0x300`，即 `0x501`）。
  PCAN-View 按 ID 分组，**同一 ID 只显示一行、只保留最新一帧**，NACK 刚发出就被下一个 ACK 覆盖。
- **修复**：`nakHeader.StdId = NODE_ID + 0x400u`（A `0x601` / B `0x602`），NACK 独立成行。
  改完立刻看到 `602h 51 00 07 48 ...`（块 7，从第 72 片重发），且 `Count=1` —— 一次就恢复。
- **代价**：多烧两轮板、多花 20 分钟，期间一度怀疑"重传根本没实现"。
- **教训**：**CAN ID 不只是地址，也是频道。** 不同语义（数据 / 心跳 / 分片 / ACK / NACK）
  必须用不同 ID 段，否则在分析仪上互相覆盖，等于自己把观测能力关掉了。
  这和第 10 条（心跳和数据共用 ID）是同一个错误的第二次犯 —— 同一类问题要写进检查清单，而不是靠记忆。
